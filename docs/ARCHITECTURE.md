# FormSure architecture

FormSure is a static React 19 + Vite + TypeScript (strict) site. There is no server of our own: the browser talks to Gemini through Firebase AI Logic, and everything else runs on the device.

## Principle: Gemini reads, code decides

1. **Gemini reads.** `services/extraction.ts` sends one document to Gemini and asks for structured JSON (names, dates, document types, income, `legible`). The answer is validated against a schema (`core/extractSchema.ts`) and anything that does not fit is rejected or marked unreadable.
2. **Code decides.** `core/engine.ts` runs the rules of a _scheme pack_ on that JSON. Each rule returns `pass`, `fail`, `needs_review` or `not_evaluated`; no verdict is produced by the model. A rule is only scored when its evidence is `verified` (see `RULES.md`, generated by `npm run rules:register`).
3. **People see why.** Every check carries its rule id, evidence and a fix in English, Marathi or Hindi.

## Data flow

```
file chosen ──► services/uploadPipeline   size, type, magic bytes, strip metadata
            ──► services/readFiles        2 workers, staggered, cached per slot
            ──► services/extraction       Gemini (Firebase AI Logic) → ExtractedDocument JSON
            ──► core/engine + core/rules  scheme pack rules → AuditReport (checks, readiness %)
            ──► screens/Report | Ready    issues with evidence, or the 100 % checklist
```

Sample mode skips the first three steps and feeds `core/sample.ts` documents to the engine.

## Folder map

| Folder                    | What lives there                                                                                                                                                           |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/core/`               | Pure logic, no React: engine, rule types in `rules/`, name matching, dates (IST financial year), file validation, form schema, sample data, constants, copy                |
| `src/core/schemes/`       | Versioned scheme packs (JSON): rules, slots, evidence per rule                                                                                                             |
| `src/services/`           | Side effects: Firebase/Gemini calls, extraction with retry, upload pipeline, read scheduler, rate limiter, `api.ts` (the facade the UI uses)                               |
| `src/hooks/`              | App state: `flowReducer` (all state transitions), `useFlow` (the controller) and its small hooks (`useAuditRun`, `useFileIntake`, `useDocumentReader`, `useSlotStates`, …) |
| `src/screens/`            | One component per screen: Landing, Scheme, Upload, Audit, Report, Ready                                                                                                    |
| `src/components/`         | Presentational pieces grouped by screen, plus `Modal`, `Ring`, `Confetti`, icons                                                                                           |
| `e2e/`                    | Playwright + axe browser tests                                                                                                                                             |
| `RULES.md`, `SECURITY.md` | Generated rule register with evidence; security and privacy notes                                                                                                          |

## Rules of the code base

- `core/` never imports React or `services/`; screens never call Gemini directly (they go through `useFlow`).
- Functions stay under complexity 10 and 60 lines, files under 200 lines (ESLint, tests excluded); there are no `eslint-disable` comments.
- Magic numbers live in `core/constants.ts` or as named constants next to their one use, with a JSDoc line.
- Documents never leave the browser except to Gemini, only after the applicant consents, and are dropped on `pagehide`.
